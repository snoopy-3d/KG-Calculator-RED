# Данные для бота-калькулятора прокачки Kingdom Guard

Извлечено 01.11.2026 из установленной Erida2 2.0.29. Источник: папка GameData. Программа не запускалась, установка не изменялась. В набор входят только игровые справочники, без аккаунтов, сессий и авторизации.

## Содержимое

- `raw/` — 15 исходных JSON без изменения байтов.
- `tables/` — CSV для просмотра и импорта. Вложенные структуры сохранены JSON в ячейках; исходные JSON предпочтительнее для бота.
- `catalog.json` — разделы, число записей, поля и примеры.
- `manifest.json` — версия источника, размеры и SHA-256. Совпадение всех копий с оригиналами проверено.

## Правила интеграции

1. Загружать исходные JSON как справочники. Не подставлять 0 вместо отсутствующего уровня, предмета или цены.
2. Группировать строки по всем измерениям механики: например, quality для эмблем; tier и part для снаряжения; type для магии. Нельзя складывать разные ветви одной таблицы.
3. Для словаря cost суммировать отдельно каждый ID предмета. Пример forge.curve: tier=1, level=2 содержит cost={"20010007":1}. Не объединять разные ID в один «материал».
4. Проверять ограничения castle, season, unlock и технологические требования там, где они присутствуют. Поле с нулём сохранять как в источнике, не придумывать его значение.
5. После проверки направления стоимости использовать сумму цен всех переходов от текущего состояния до целевого. Если цена строки L относится к получению уровня L, формула: сумма cost(L) для current < L <= target. Если строка описывает выход из L — диапазон другой. Это условная формула, а не подтверждённая логика Erida.
6. Если power — итоговая сила на уровне, прирост равен power(target)-power(current), а не сумме power. Указанная семантика требует проверки на игровом примере. Бонусы также нельзя автоматически складывать между механиками.
7. Для бюджета после подтверждения переходов последовательно вычитать стоимость каждого доступного перехода по каждому предмету; остановиться при недостатке любого ресурса или невыполненном требовании.
8. Отдельно показывать базовую стоимость, имеющиеся ресурсы и нехватку max(0, стоимость-запас). Скидки, события, VIP и множители применять только по подтверждённым правилам.

## Что ещё не подтверждено

- Направление стоимости строки и индексация массивов замка и опыта героя. В castle_costs.indexed.csv поле level_label_candidate — только кандидат, source_index — точный исходный индекс.
- Значения experience: затраты на отдельный переход или накопленный опыт; деление на materialExp и округление нельзя включать без проверки.
- Единицы скалярных cost (например, кузница и эмблемы), если ID ресурса не указан в самой строке.
- Полная таблица стоимости звёзд/возвышения героев: stages и stars сами по себе не доказывают стоимость в осколках.
- Русские названия всех предметов и навыков. name_key, Skill_name и skillPro — ключи локализации, не готовые названия. Сохранять ID до получения соответствующего словаря.
- Совпадение с актуальной игрой: ряд JSON содержит client=1.0.595.8070. Это снимок установленного приложения, не онлайн-проверенная база.

Пример данных: forge.levels содержит level=1, cost=5, power=2500 и level=2, cost=5, power=5000. Если подтвердится модель «цена достижения уровня», переход 1→2 стоит 5 единиц базового ресурса; при модели итоговой силы прирост составит 2500. Эти условия нужно проверить до выдачи пользователям как точного игрового расчёта.

## Рекомендуемый первый этап бота

Сначала подтвердить по двум соседним уровням замка, кузницы и одной ветви ведьмы направление стоимости и ID ресурсов. Затем реализовать выбор механики/ветви, текущий и целевой уровни, стоимость по ресурсам и нехватку. Герои, переходы ступеней и зависимости узлов требуют отдельных правил. Извлечённые данные не являются готовой реализацией бота.
